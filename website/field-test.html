We tested our PII proxy on a real AI session. Here's what we found.

A live Cline session, fake client data, and a local scrubbing proxy between the model and everything else.

October 26, 2026 · 12 min read

The setup

ClaimCheck sits between your AI coding assistant and the model provider. Everything the assistant sends — prompts, file reads, pasted logs — gets scrubbed locally before it reaches the provider, and the provider's response gets the real values restored on the way back. The mapping never leaves your machine.

We pointed Cline at the proxy with a fake client record and ran a live session. The data looked like real payroll work: a FEIN, an SSN, a bank account, a client name, a company, dates, a VIN, an IMEI, a card number. All fake — but shaped like the real thing.

What worked: everything with a label

The FEIN was masked. The SSN was masked. The bank account, the email, the password, the API key, the dates, the VIN, the IMEI — thirteen value types across the session, every one replaced with a stable placeholder before the request left the machine.

The model confirmed it. Asked to list what it received, it enumerated the placeholders — [FEIN_2], [SSN_2], [ACCOUNT_2] — and noted which values arrived as plain text instead. Asked to state the FEIN, it refused: "no actual FEIN number was provided, so I can't tell you the real digits, and I won't invent one."

That refusal is the product working. The model couldn't state the FEIN because the FEIN wasn't in its context. The only place the real digits existed was the user's machine.

The probe that proves it

Here's the test we now run on every PII tool we evaluate — including ours. Send the model fake data, then ask it to spell the sensitive value backwards, digit by digit.

If the tool scrubbed correctly, the model only ever saw a placeholder token. It can't reverse what it never had. In our test, the model spelled the placeholder label backwards — proving the only "FEIN" in its context was the tag [FEIN_2], not the number.

If the tool didn't scrub, the model spells the real digits backwards without hesitation. No ambiguity, no interpretation — the model either had the data or it didn't.

Run this probe on any PII tool you use. It's model-side, unambiguous in both directions, and immune to the "restored vs never-scrubbed" confusion that makes client-side testing hard.

What didn't work: the name layer was silently dead

The client's name — the one value with no format to pattern-match — reached the model in plain text. Not because the scrubber failed; because the layer that catches free-text names (a local NER model) had silently disabled itself on the test machine.

The root cause: a stale native runtime library from an earlier build, sitting in the install folder, shadowing the newer one bundled with the current exe. The NER engine initialized against the old library, threw a version error, caught it, and turned itself off — while the status output kept saying it was on, because the model files were fine. Only the runtime that runs them wasn't.

The model's own answer made the gap visible: asked about the client's name, it stated the letter count and the last letter with confidence — something it couldn't have done from a placeholder token.

The lesson generalizes: any tool with a "silently degrade on failure" path will eventually degrade silently. If a protection layer can turn itself off, the status output must say so — loudly, in the same place the "on" claim lives.

The cost problem nobody budgets for

Even when the name layer works, it's the most expensive part of the pipeline by two orders of magnitude. The regex tier over a full 1M-token request: 1.4 seconds, all 26 recognizers. The NER model over the same text: 3–16 minutes on CPU — thousands of inference windows, each a full model pass.

That's why ClaimCheck ships with the name layer off by default. The regex tier catches every labeled value at any context size for free. The NER layer is opt-in — for sessions with real client data where free-text names are the threat that matters.

The honest framing: labeled values (FEINs, SSNs, accounts, cards) are the high-precision, high-recall layer — the values that identify a business. Free-text names are the layer that identifies a person. Both matter. They don't cost the same to protect.

The takeaway

ClaimCheck catches what it catches and tells you what it doesn't. The regex tier: 26 value types, deterministic, no cap, effectively free at any context size. The name layer: probabilistic, English-trained, off by default, opt-in when the threat is live.

Run the reversal probe on whatever PII tool you use — ours or anyone else's. If the model can't spell the sensitive value backwards, the tool worked. If it can, you have a leak and a conversation to have with the vendor.
